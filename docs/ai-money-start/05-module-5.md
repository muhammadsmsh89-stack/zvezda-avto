Каркас WHAT/WHY/HOW/EXAMPLE/TEMPLATE/YOUR TURN/DONE WHEN сохранён; внутри HOW — 23 плотных секции (24-я секция брифа, YOUR TURN, вынесена в общий блок YOUR TURN модуля).

## WHAT

Превратить навык и портфолио в понятное коммерческое предложение. После модуля есть: чёткая ЦА, одно предложение об услуге, понятный deliverable, scope, срок, количество правок, стартовая цена, 3 package options (STARTER/CORE/PLUS), границы работы и готовый текст предложения клиенту.

**Главный принцип: не продавай навык. Продавай понятный результат и deliverable.**

## WHY

### SECTION 1 — WHY SERVICES DON'T SELL

«Делаю сайты» · «Работаю с ИИ» · «Создаю контент» · «Делаю презентации» · «Пишу тексты» · «Занимаюсь дизайном» — клиент не понимает: для кого, что конкретно получит, какая задача решается, какой объём, сколько времени, зачем ему это вообще.

```
SKILL ≠ OFFER

SKILL:    «Я умею делать сайты»
SERVICE:  «Landing Page»
OFFER:    «Соберу одностраничный сайт для стоматологии с услугами,
           врачами, блоками доверия и понятным переходом к записи»
```

## HOW

### SECTION 2 — OFFER FORMULA

```
I HELP [CLIENT TYPE] WITH [PROBLEM / TASK] BY DELIVERING [SPECIFIC DELIVERABLE] WITHIN [TIMEFRAME]

«Помогаю [КТО] решить [КОНКРЕТНАЯ ЗАДАЧА] с помощью [DELIVERABLE] за [СРОК / ФОРМАТ РАБОТЫ]»
```

Не обязательно втискивать все четыре части в одно длинное предложение — оффер должен звучать естественно.

```
ПЛОХО:  «Помогаю бизнесам увеличивать продажи с помощью современных AI-технологий»
ЛУЧШЕ:  «Разрабатываю лендинги для локального бизнеса: структура, текст,
         адаптивная версия и форма заявки»
```

### SECTION 3 — WHO EXACTLY DO YOU SELL TO?

«Моя ЦА — бизнес» не считается. **CLIENT FOCUS BUILDER:**

```

WHAT THEY SELL:              [ ]
WHO THEIR CUSTOMER IS:        [ ]
COMMON PROBLEM:               [ ]

```

Пример: SERVICE — Landing Pages · CLIENT TYPE — локальный бизнес · NICHE — стоматологии · COMMON PROBLEM — есть трафик/карточки/соцсети, но нет понятной страницы, куда вести пользователя.

**Важно:** это гипотеза для проверки на конкретном лиде, а не утверждение, что проблема есть у каждой стоматологии.

### SECTION 4 — RESULT VS DELIVERABLE

```
BUSINESS RESULT:  больше заявок      DELIVERABLE:  landing page
```

Новичок гарантирует только то, что реально контролирует.

| CAN CONTROL | CANNOT CONTROL |
|---|---|
| структура и текст лендинга | сколько трафика приведёт реклама клиента |
| дизайн и адаптивность страницы | бюджет клиента на рекламу |
| срок сдачи со своей стороны | качество продукта/услуги клиента |
| количество и логика правок | цена, которую установит клиент |
| техническая работоспособность (кнопки, формы, ссылки) | работа отдела продаж клиента |
| точность включённой информации из брифа | реальный объём трафика на сайт/канал |
| формат и упаковка deliverable | действия конкурентов |
| соответствие согласованному scope | сезонность спроса в нише |
| ясность коммуникации в процессе | готовность клиента опубликовать/использовать материал |
| качество текста/визуала в рамках компетенции | изменения алгоритмов соцсетей/поисковиков |

Нельзя обещать «сделаю вам +30% продаж». Можно — «соберу лендинг по согласованной структуре с адаптивной версией и формой заявки».

### SECTION 6 — SCOPE CREEP

«А давайте ещё вот это» + «а можете ещё страницу» + «а добавьте ещё 10 постов» = проект вырос в 2 раза.

```
NEW DELIVERABLE = NEW SCOPE
```

Небольшие корректировки внутри согласованного результата — правки. Новый результат — дополнительная работа.

| REVISION | NEW SCOPE |
|---|---|
| поменять цвет кнопки | добавить вторую страницу |
| переформулировать 2 предложения | написать текст для другой аудитории с нуля |
| уменьшить шрифт заголовка | редизайн всей структуры лендинга |
| поменять 3 слайда местами | добавить ещё 5 новых слайдов |
| исправить опечатку в посте | написать ещё 10 постов сверх пакета |
| смягчить тон в сценарии | сценарии под другую платформу (TikTok вместо Reels) |
| поменять CTA-кнопку | добавить форму подписки + интеграцию с CRM |
| другой заголовок раздела | перевести материал на другой язык |

### SECTION 7 — REVISION POLICY

```
2 ROUNDS OF REVISIONS

ROUND ≠ одна маленькая правка.
Round = клиент собирает список замечаний и присылает одним сообщением/документом.

Version 1 → Client Feedback #1 → Revision → Client Feedback #2 → Final Revision
```

После этого — дополнительные изменения по отдельной договорённости. Политика нужна не для жёсткости, а чтобы обе стороны понимали процесс.

### SECTION 8 — PRICE BUILDER

Ценообразование — **решение, а не физический закон.** Цена складывается из:

```
BASE SCOPE + COMPLEXITY + DEADLINE + REVISIONS + ADDITIONAL DELIVERABLES
+ EXPERIENCE / PROOF + CLIENT CONTEXT
```

Вопросы перед назначением цены:

```
☐ Сколько времени займёт работа?
☐ Что именно входит?
☐ Насколько сложный проект?
☐ Есть ли дополнительные требования?
☐ Насколько уверенно я могу выполнить scope?
☐ Есть ли у меня релевантные кейсы?
☐ Сколько правок?
☐ Насколько срочно?
☐ Какую ценность deliverable имеет для этого типа клиента?
```

### SECTION 9 — STARTING PRICE

**TEST PRICE** — цена, которая: не заставляет работать бесплатно · позволяет спокойно выполнить scope · соответствует текущему уровню · не требует изображать экспертность, которой нет · может быть повышена после доказательств.

> Примерные диапазоны ниже — обучающие примеры. Это не рыночный прайс-лист. Реальные цены отличаются по стране, нише, качеству и объёму.

| Услуга | ENTRY (пример) | PROVEN (пример) | STRONGER (пример) |
|---|---|---|---|
| Landing Pages | узкий scope, мало кейсов · ~3 000 ₽ | 2–3 реальных клиента с отзывами · ~8 000 ₽ | специализация в нише + доп. deliverables (SEO, интеграции) · 14 000 ₽+ |
| Commercial Presentations | ~2 500 ₽ | ~6 000 ₽ | ~10 000 ₽+ |
| Lead Magnets / PDF | ~2 000 ₽ | ~5 000 ₽ | ~9 000 ₽+ |
| Telegram Content Packs | ~3 000 ₽ | ~7 000 ₽ | ~11 000 ₽+ |
| Short-Form Video Scripts | ~2 000 ₽ | ~5 000 ₽ | ~8 000 ₽+ |

Логика перехода: ENTRY — узкий scope, доказательств мало; PROVEN — есть реальные завершённые проекты и отзывы; STRONGER — сильнее портфолио + процесс + специализация + больший scope. **Нет гарантии**, что переход происходит автоматически после N клиентов.

### SECTION 10 — NEVER WORK FOR FREE?

```
FREE FULL PROJECT           vs        SMALL DEMONSTRATION / AUDIT / SAMPLE
(запрещено)                            (допустимо как sales tool, если scope ограничен)
```

Плохо — сделать весь сайт бесплатно «чтобы клиент посмотрел». Допустимо — короткий аудит, 1 concept-секция, небольшой пример, демонстрационный фрагмент, если пользователь сам решил использовать это как инструмент продажи и заранее ограничил scope.

**FREE SAMPLE BOUNDARY:** клиент не должен получить практически готовый коммерческий результат бесплатно — фрагмент должен быть явно меньше полного deliverable.

### SECTION 11 — 50% PREPAYMENT

Для небольших fixed-scope проектов: **50% до старта + 50% до финальной передачи.** Для более крупных проектов — milestones. Зачем предоплата: подтверждает намерение · резервирует время · снижает риск бесплатной работы · формализует старт.

```
Scope approved → Price approved → Payment terms approved → Prepayment → Work starts
```

Полноценная работа не начинается до согласования условий.

### SECTION 12 — PACKAGE STRATEGY

STARTER/CORE/PLUS — не манипуляция ценой, а варианты scope. Не «плохой/нормальный/хороший», а «минимальная задача / основной рекомендованный scope / расширенный результат».

### SECTION 14 — PRICE ANCHOR WITHOUT MANIPULATION

Не нужно: фейковая старая цена («было 30 000 ₽, сейчас 9 990 ₽») · «осталось 2 места», если неправда · искусственный таймер. Вместо этого цена объясняется scope: STARTER — меньше deliverables, CORE — основной объём, PLUS — расширенный объём. Ценность реальная, а не нарисованная маркетингом.

### SECTION 15 — HOW TO SAY THE PRICE

Вместо «ну где-то 10–15 тысяч, смотря как получится»:

| Ситуация | Формулировка |
|---|---|
| Обычный проект | «По описанному объёму стоимость составит [X] ₽. В неё входит [scope], срок [N] дней, два раунда правок. Старт — после 50% предоплаты.» |
| Клиент спрашивает только цену | «Чтобы назвать точную стоимость, нужно понять объём: [2–3 уточняющих вопроса]. Ориентировочно формат стоит от [X] до [Y] ₽ в зависимости от объёма.» |
| Клиент ещё не дал scope | «Пока рано называть точную цифру — предлагаю сначала зафиксировать, что именно нужно: [вопросы]. После этого пришлю точную стоимость и срок.» |
| Клиент хочет срочно | «Могу сделать быстрее — за [укороченный срок], стоимость с учётом срочности — [X] ₽.» |
| Клиент хочет доп. deliverables | «Это уже за рамками текущего scope, добавлю отдельным пунктом — [+X] ₽ к итоговой стоимости.» |
| Клиент просит скидку | «Могу предложить более компактный вариант в рамках STARTER за [X] ₽ — либо полный CORE за [Y] ₽. Что вам актуальнее?» |
| Клиент говорит «дорого» | «Понимаю. Стоимость собрана из [scope]. Если бюджет сейчас ограничен — есть более узкий STARTER-вариант за [X] ₽.» |
| Клиент сравнивает с другим исполнителем | «У каждого исполнителя свой scope и процесс — могу прислать, что именно входит в мою цену, чтобы сравнение было честным.» |
| Знакомый клиент | «Раз мы знакомы — могу сделать по стартовой цене [X] ₽, но по тому же процессу и scope, что и для любого клиента: [scope, сроки, правки].» |
| Повторный клиент | «Рад(а) снова поработать. Формат и цена — как в прошлый раз, [X] ₽, либо могу предложить более широкий CORE/PLUS, если нужен больший объём.» |

### SECTION 16 — DON'T ASK "WHAT IS YOUR BUDGET?" TOO EARLY

Сначала — задача, scope, срок, ожидания. Потом — бюджет, естественно:

```
1. «Чтобы предложить подходящий формат — рассматриваете более компактный
    вариант или полноценную реализацию?»
2. «Есть ли ориентир по бюджету, чтобы предложить подходящий пакет?»
3. «Вам важнее уложиться в определённую сумму или получить максимальный
    результат, даже если это чуть дороже?»
4. «Если сумма выше [диапазон] — какой вариант вам комфортнее рассмотреть?»
5. «Хотите, пришлю 2–3 варианта под разный бюджет, и вы выберете, что подходит?»
```

### SECTION 22 — PRICE GROWTH

Нет гарантированной лестницы («первый клиент 10k, второй 20k, третий 40k»). Цена растёт, когда появляются: реальные кейсы · отзывы · более сильный процесс · специализация · скорость · более широкий scope · больше ответственности · доказанный спрос.

**PRICE REVIEW CHECKPOINT** (после каждых 2–3 завершённых проектов):

```

☐ Повысился ли спрос?

```

### SECTION 23 — RED FLAGS

Не браться за проект, если: непонятно, что нужно · клиент требует полноценную бесплатную работу · отказывается фиксировать scope · требует бесконечных правок · просит соврать/подделать · задача сильно выше компетенции · ожидается гарантированный бизнес-результат вне контроля исполнителя · нет договорённости по оплате · клиент постоянно добавляет deliverables до старта. Это не повод для паранойи — просто признаки плохого fit.

# QUALITY CHECK

**1. Понимает ли новичок разницу Skill / Service / Offer?**
Да — Section 1 строит модуль именно на этой разнице с самого начала (SKILL ≠ OFFER).

**2. Понятно ли, что получает клиент?**
Да — DELIVERABLE зафиксирован отдельным полем в Client Focus Builder, Scope Builder, Offer Builder и во всех 5 примерах Section 21.

**3. Умеет ли пользователь ограничивать scope?**
Да — Scope Builder (Section 5) + Scope Creep (Section 6) с 8 парами REVISION vs NEW SCOPE.

**4. Не обещает ли он результат бизнеса?**
Нет — Section 4 прямо разводит BUSINESS RESULT и DELIVERABLE с таблицей CAN/CANNOT CONTROL из 10 пар.

**5. Есть ли нормальная политика правок?**
Да — Section 7, с чётким workflow Version1→Feedback→Revision→Feedback2→Final.

**6. Помогает ли модуль назначить цену, а не только говорит «цена зависит»?**
Да — Section 9 даёт конкретный TEST PRICE и ENTRY/PROVEN/STRONGER лестницу с примерами по всем TOP 5, а не только абстрактную формулу.

**7. Не выдаются ли учебные цены за объективный рынок?**
Нет — при каждом появлении цифр (Sections 9, 13, 21) стоит явная пометка «пример учебной цены / не рыночный факт».

**8. Есть ли STARTER / CORE / PLUS для всех TOP 5?**
Да — Section 13, полностью для всех пяти услуг, с реалистичным scope в границах компетенции из Module 3.

**9. Понимает ли пользователь принцип предоплаты?**
Да — Section 11, с процессом Scope→Price→Payment terms→Prepayment→Work starts.

**10. Может ли он после модуля написать клиенту конкретное предложение?**
Да — Section 19 (Message Version) и Section 21 дают готовые к использованию формулировки.

**11. Не перегружен ли модуль теорией?**
Каждая секция заканчивается шаблоном, таблицей или готовой формулировкой — нет секции без прикладного вывода; 23 секции плотные, но не текстовые «простыни».

**12. Готов ли он после этого перейти к поиску первых лидов?**
Да — DONE WHEN закрывает все элементы, нужные для Дня 8 (готовое сообщение с предложением, зафиксированная цена и scope).
