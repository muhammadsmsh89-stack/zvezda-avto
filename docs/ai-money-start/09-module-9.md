# AI MONEY START — GUIDE
## MODULE 9 — CLIENT DELIVERY SYSTEM (черновик, близкий к финальному)

**Формат:** предпоследний основной модуль. Ориентир Guide-части — 6–8 плотных PDF-страниц. Полные библиотеки сообщений и брифов — в `09a-module-9-delivery-templates.md`.

**Привязка к плану:** сразу после WON. Не отдельная неделя delivery — как только сделка закрыта, кикофф идёт сразу же, outreach по возможности продолжается параллельно.

---

## WHAT

```
PREPAYMENT / START CONFIRMATION → BRIEF → MATERIALS → PROJECT PLAN →
PRODUCTION → INTERNAL QA → CLIENT REVIEW → REVISIONS → APPROVAL →
FINAL PAYMENT → HANDOFF
```

Выполнить проект профессионально, не потерять контроль над scope и нормально получить финальную оплату.

## WHY

Клиент оплатил — новичок сразу открывает редактор и начинает делать. Через несколько часов выясняется: нет логотипа, нет фото, непонятны услуги, клиент хотел другой стиль, нужен доп. блок, решение согласует другой человек.

```
DON'T START PRODUCTION UNTIL INPUTS ARE CLEAR
```

Перед production нужны: Scope · Goal · Materials · References · Decision-maker · Deadline · Delivery format.

---

## HOW

### SECTION 1 — PROJECT KICKOFF

После предоплаты — сообщение, которое подтверждает получение, фиксирует старт, называет следующий шаг, запрашивает материалы и намекает на срок после их получения:

```
«Оплату получил(а), спасибо. Тогда фиксирую старт проекта. Следующий
шаг — собрать материалы и уточнить несколько деталей по содержанию.
Ниже отправлю короткий бриф. После получения материалов подтвержу
рабочий график и дату первой версии.»
```

Ещё 5 вариантов (обычный/landing/presentation/content/срочный/repeat client) — Templates T1.

### SECTION 2 — THE MINIMUM BRIEF

Не 40 вопросов — универсальный минимум:

```
BUSINESS / PROJECT   — что это за бизнес/проект?
AUDIENCE              — для кого?
GOAL                   — что должен сделать deliverable?
OFFER / PRODUCT         — что продаём/объясняем?
CONTENT                  — что обязательно должно присутствовать?
CTA                        — какое действие должен сделать пользователь?
STYLE                       — есть ли пожелания/references?
MATERIALS                    — что уже есть?
RESTRICTIONS                  — что нельзя использовать/менять?
DECISION MAKER                  — кто утверждает?
DEADLINE                          — когда нужен результат?
```

Дополнительные вопросы по каждой из TOP 5 услуг (Landing/Presentation/Lead Magnet/Telegram/Scripts) — Templates T2, без дублирования универсальных пунктов выше.

### SECTION 3 — CLIENT MATERIALS CHECKLIST

Возможные материалы: логотип · брендбук · фотографии · тексты · услуги · цены · контакты · ссылки · кейсы · отзывы · статистика (только если подтверждена клиентом) · юридический текст, если предоставлен клиентом · references · доступ к аккаунту, если реально нужен.

Не просить пароли без необходимости — предпочитать безопасные способы доступа/приглашения там, где сервис это поддерживает.

### SECTION 4 — SOURCE OF TRUTH

```
VERIFIED PUBLIC   —  можно проверить публично
CLIENT PROVIDED   —  клиент сообщил сам
PLACEHOLDER        —  временная заглушка, будет заменена
UNKNOWN             —  данных нет

UNKNOWN ≠ permission to invent
```

Особенно важно для цифр, наград, сертификатов, результатов, отзывов, цен, характеристик. «У нас 12 лет опыта» от клиента — CLIENT PROVIDED, можно использовать. То же самое, придуманное ИИ — нельзя.

### SECTION 5 — PROJECT BOARD

```
TO DO → IN PROGRESS → WAITING FOR CLIENT → REVIEW → REVISION → DONE
```

Любой простой инструмент (Notion/Trello/таблица/чек-лист) — не нужна сложная CRM. Главное — у каждой задачи есть статус.

### SECTION 6 — DELIVERY PLAN (по TOP 5)

| Услуга | Этапы |
|---|---|
| Landing Pages | Inputs → Structure → Copy draft → Visual direction → Build → Mobile → QA → Client review → Revisions → Handoff |
| Commercial Presentations | Inputs → Storyline → Content → Design direction → Slides → QA → Review → Revisions → Export |
| Lead Magnets / PDF | Inputs → Structure → Copy → Design → QA → Review → Revisions → Export |
| Telegram Content | Inputs → Content pillars → Draft posts → Calendar → QA → Review → Revisions → Handoff |
| Short-Form Scripts | Inputs → Angle map → Draft scripts → QA → Review → Revisions → Handoff |

### SECTION 7 — FIRST VERSION ≠ ROUGH MESS

Не отправлять хаотичный полуфабрикат со словами «ну вот примерно». First Version должна соответствовать согласованному scope, быть достаточно законченной для оценки, пройти внутренний QA и иметь понятные места для feedback — не обязательно быть финальной, но клиент должен видеть профессиональный результат.

### SECTION 8 — INTERNAL QA BEFORE CLIENT (PRE-SEND CHECK)

```
CONTENT         ☐ нет placeholders  ☐ нет выдуманных фактов  ☐ тексты вычитаны
SCOPE           ☐ всё согласованное присутствует  ☐ лишний scope не добавлен
CONSISTENCY     ☐ единый стиль  ☐ одинаковые названия  ☐ единый tone
TECHNICAL       ☐ links  ☐ buttons  ☐ mobile  ☐ exports  ☐ file opens  ☐ dimensions
BUSINESS LOGIC  ☐ понятно предложение  ☐ понятен CTA  ☐ deliverable решает задачу
```

### SECTION 9 — TOP 5 QUALITY CHECKS (client delivery QA, не Module 3 повторно)

| Услуга | Проверить |
|---|---|
| Landing | responsive · buttons · links · CTA · контакты · text overflow · формы, если применимо |
| Presentation | порядок слайдов · читаемость текста · единое форматирование · нет пропущенных ассетов · качество экспорта |
| PDF | пагинация · читаемость · ссылки · CTA · экспорт · нет обрезанных элементов |
| Telegram | фактическая точность · тон · форматирование · CTA · нет дублей постов |
| Scripts | хук · логика повествования · читаемость на слух · CTA · нет выдуманных заявлений |

### SECTION 10 — HOW TO SEND FIRST VERSION

```
WHAT'S READY → WHAT TO REVIEW → HOW TO GIVE FEEDBACK → DEADLINE / NEXT STEP
```

```
«Первая версия готова. Сейчас предлагаю посмотреть прежде всего
структуру, тексты и общую подачу. Соберите, пожалуйста, замечания
одним списком — после этого внесу первый раунд правок.»
```

Ещё 4 варианта — Templates T5.

### SECTION 11 — FEEDBACK SYSTEM

«Что-то не нравится» превращается в конкретику через уточнение:

```
Vague:      «Сделайте современнее»
Clarifying: «Есть пример того, что вы называете современным?»
```

Ещё 7 пар VAGUE FEEDBACK → CLARIFYING QUESTION — Templates T3.

### SECTION 12 — REVISION ROUNDS

```
CLIENT FEEDBACK → CONFIRM UNDERSTANDING → REVISION → SEND UPDATE
```

Перед правками — объединить комментарии. Не реагировать хаотично на «ещё здесь», «а ещё тут», «ой, ещё забыл»:

```
«Соберите оставшиеся замечания в один список, чтобы я внёс их одним
раундом и ничего не потерял.»
```

### SECTION 13 — REVISION VS NEW SCOPE

```
Client: «Добавим ещё страницу»
Ответ:  «Да, можем. Это уже дополнительный deliverable вне текущего
         scope. Я оценю объём отдельно, и добавим его к проекту.»
```

Ещё 7 спокойных ответов (доп. посты, доп. сценарии, новый формат, новая презентация, переработка после утверждения, срочная новая задача, новый язык/версия) — Templates T4.

### SECTION 14 — CHANGE REQUEST

```
REQUEST → IS IT REVISION?
   YES → текущий scope
   NO  → оценка доп. scope → изменение цены/срока → согласие клиента → работа
```

Не делать новую работу до согласования изменения.

### SECTION 15 — CLIENT DELAYS

```
PROJECT TIMELINE DEPENDS ON CLIENT INPUTS
```

Если необходимые материалы задержаны — дедлайн может сдвигаться, но это должно быть заранее понятно клиенту. Пример: «Добрый день! Напоминаю — для продолжения нужны материалы: [список]. Как будут готовы, подтвержу график.» Ещё 4 сообщения (feedback reminder, project paused, new timeline, restart after delay) — Templates T6.

### SECTION 16 — USER DELAYS

Если пользователь понимает, что опаздывает — не исчезать. Сообщить заранее, объяснить без длинных оправданий, дать новый реалистичный срок:

```
«Хочу заранее предупредить — первая версия будет готова на день
позже согласованного, [новая дата]. Дальше буду держать в курсе.»
```

Ещё 2 примера — Templates T7.

### SECTION 17 — CLIENT COMMUNICATION RULE

```
NO SURPRISES
```

Клиент должен знать: что происходит, что нужно от него, какой следующий этап, есть ли изменение срока, когда следующая точка контакта. Не обязательно писать апдейт ежедневно, но исчезать на неделю без договорённости нельзя.

### SECTION 18 — FINAL APPROVAL

```
«Если по этой версии всё согласовано, фиксируем её как финальную и
переходим к передаче материалов.»
```

Не просто отправить файлы без подтверждения. Ещё 3 варианта — Templates T8.

### SECTION 19 — FINAL PAYMENT

Если модель 50/50 — остаток обычно запрашивается после утверждения результата и до передачи финальных editable/source материалов, если именно так было согласовано. Это не универсальный юридический стандарт — условия должны соответствовать предварительной договорённости и применимым правилам.

```
«Финальная версия утверждена — отправляю реквизиты на оставшуюся
часть оплаты, [X] ₽. После поступления передаю все материалы.»
```

Ещё 4 варианта — Templates T9.

### SECTION 20 — HANDOFF

Не «final-final2-LAST.zip». Структура:

```
01_FINAL
02_SOURCE   — если входит
03_ASSETS   — если входят
04_README   — что передано, ссылки, доступы, инструкции, что делать
              дальше, support boundary
```

**По TOP 5:** Landing — опубликованный URL/согласованные файлы, исходники если включены, передача доступа, базовая инструкция · Presentation — PDF, editable-файл если включён, шрифты/ассеты только где позволяет лицензия · Lead Magnet — финальный PDF, editable-исходник если включён, проверенные ссылки · Telegram — документ с контентом, календарь, форматирование, ссылки на ассеты · Scripts — документ со сценариями, content angle map, статусы/категории, продакшн-заметки если включены. Не передавать материалы, лицензия на которые этого не позволяет.

### SECTION 21 — ACCESS & OWNERSHIP

До старта — понимать: какие исходники входят, какие аккаунты принадлежат клиенту, какие лицензии используются, что именно передаётся. При завершении — удалить ненужные чувствительные доступы, не сохранять пароли, передать ownership там, где это предусмотрено.

### SECTION 22 — SUPPORT BOUNDARY

Через месяц клиент может написать «а поменяйте ещё одну штуку» — заранее понимать, что входит после handoff:

```
INCLUDED SUPPORT:      [ ]  (например: 7 дней на исправление технических ошибок,
                              если пользователь решил включить такую поддержку)
NOT INCLUDED:          новый контент / редизайн / новые deliverables
```

Не универсальная норма — решение пользователя по каждому проекту.

### SECTION 23 — PROJECT COMPLETION MESSAGE

```
PROJECT COMPLETE → WHAT WAS DELIVERED → WHERE → SUPPORT → NEXT STEP
```

Не просить отзыв в этом же сообщении, если это выглядит перегруженно — отзывы и рекомендации отдельно разберёт Module 10.

### SECTION 24 — DELIVERY RED FLAGS

Уточнить ситуацию, если: просят скрыть/подделать информацию · появляются незаконные требования · требуют нелицензированные материалы · хотят новые deliverables без изменения scope · требуют не нужные для проекта доступы · пытаются значительно изменить задачу после старта · отказываются платить согласованный milestone, но требуют продолжения · просят передать финальные материалы до предусмотренного договорённостью этапа оплаты.

### SECTION 25 — CLIENT DELIVERY BOARD

```
CLIENT:              [ ]
PROJECT:             [ ]
STATUS:              [ ]
START DATE:          [ ]
TARGET DATE:         [ ]
CURRENT STAGE:       [ ]
WAITING FOR:         [ ]
NEXT ACTION:         [ ]
NEXT CONTACT DATE:   [ ]
PAYMENT STATUS:      [ ]
REVISION ROUND:      [ ]
SCOPE CHANGE:        [ ]
FINAL APPROVAL:      [ ]
HANDOFF:             [ ]
```

Не новая CRM — карточка активного проекта внутри существующей системы (Lead Tracker/Project Board).

### SECTION 26 — DO NOT OVERDELIVER INTO BURNOUT

«Если сделаю в 3 раза больше, клиент будет счастлив» — и бесплатно добавляются страницы, посты, дизайн, ночная работа. Это создаёт плохие ожидания на будущее.

```
DELIVER WHAT WAS PROMISED + DO IT WELL
```

Небольшой бонус допустим по желанию, но он должен быть намеренным, ограниченным и не заменять нормальное ценообразование.

# QUALITY CHECK

**1. Понимает ли новичок, что делать сразу после предоплаты?**
Да — Section 1 (Project Kickoff) даёт готовую формулу первого сообщения сразу после оплаты.

**2. Не начинает ли production до получения inputs?**
Нет — WHY-блок и Section 2–3 прямо требуют Brief и Materials до начала работы: DON'T START PRODUCTION UNTIL INPUTS ARE CLEAR.

**3. Достаточно ли короткий Brief?**
Да — Section 2 ограничен 11 универсальными пунктами, без 40 вопросов.
